# Architecture Design — Add a cancel booking endpoint that refunds payment

- Workflow: `ai-dev-cd7552ce2fac`
- Repository (logical): `booking-service`
- Module: `payment`

## Requirement

Add a cancel booking endpoint that refunds payment

## Decision

Add an OpenAPI-first POST /v1/bookings/{bookingId}/cancellation endpoint in the payment module. The generated controller delegates to a hexagonal application service that loads the BookingPayment aggregate, creates a Refund with a unique idempotency key, durably persists the refund as PENDING, then invokes the configured PaymentGateway idempotently. The refund and payment statuses are updated in the same database transaction only after the gateway confirms success. Duplicate cancellation requests with the same idempotency key return the original result without calling the gateway again.

## Constraints

- The OpenAPI contract is the source of truth; generated interface must not be manually edited and no extra request mappings may be added outside it.
- Refund idempotency must be enforced by a database unique constraint on refund.idempotency_key; duplicate requests with the same key must not trigger a second gateway call.
- Monetary values must use DECIMAL plus ISO-4217 currency, never floating point, and the refund amount must be less than or equal to the original paid amount.
- The payment gateway must be called only after the refund row is durably persisted as PENDING, and the gateway call must include the idempotency key so retries after a crash cannot double-refund.
- Automated tests must not use a production database or a real payment gateway; integration tests must use testcontainers for the database and a mocked/stubbed PaymentGateway adapter.
- Existing payment endpoints, events, and database tables must remain unchanged; this change is additive only.
