# Architecture Design — Create a tiny AWS Lambda (Node.js 22, API Gateway HTTP API) with GET /uptime returning JSON {"uptimeSeconds": <number of seconds since the function container started>}. Any other method returns 405. No UI.

- Workflow: `ai-dev-8439078d4d3d`
- Repository (logical): `time-api`
- Module: `lambda`

## Requirement

Create a tiny AWS Lambda (Node.js 22, API Gateway HTTP API) with GET /uptime returning JSON {"uptimeSeconds": <number of seconds since the function container started>}. Any other method returns 405. No UI.

## Decision

Build a zero-dependency Node.js 22 ES-module Lambda in lambda/, deployed with AWS SAM behind an API Gateway HTTP API (payload v2). Define a single function `UptimeFunction` whose HttpApi event is declared as `Method: ANY, Path: /uptime`, not `GET /uptime`. HTTP API answers an unmatched method with its own 404 and never invokes the function, so the 405 and Allow header can only come from the handler if all methods reach it. The handler stays thin. It reads requestContext.http.method and rawPath. For GET on /uptime it returns 200 with a JSON string body {"uptimeSeconds": n}. For any other method it returns 405 with `Allow: GET`, a JSON error body in the shape { error: { code, message } }, and Content-Type. Unknown paths that reach the function return 404. Container start time is captured once at module scope when the module is initialized, using a monotonic clock (process.uptime() or performance.now() captured at load). Do not use a per-invocation Date.now() baseline, and never reset the start time inside the handler. A pure function `computeUptimeSeconds(startMs, nowMs)` is split out for unit tests and returns a non-negative number. Responses set `Content-Type: application/json; charset=utf-8` and `Cache-Control: no-store`. Tests use node:test against the exported handler with realistic v2 events (GET 200, POST/PUT/DELETE/PATCH 405 with Allow, wrong path 404). They also cover the warm-invocation case: two calls in the same module instance return non-decreasing uptime, with the clock injectable or the time faked. SAM template.yaml sets explicit Runtime nodejs22.x, Timeout and MemorySize, uses no extra IAM policies beyond the default basic execution role, and has an Output with the HTTP API endpoint URL.

## Components

- lambda/template.yaml (SAM: UptimeFunction, HttpApi event Method ANY Path /uptime, Outputs with endpoint URL)
- lambda/src/handler.js (exported `handler`; method/path check; builds { statusCode, headers, body })
- lambda/src/uptime.js (module-scope container start capture; pure `computeUptimeSeconds`)
- lambda/package.json ("type": "module", `node --test` script, no runtime dependencies)
- lambda/test/handler.test.js (node:test: 200, 405 + Allow, 404, Cache-Control, content type)
- lambda/test/uptime.test.js (node:test: pure uptime computation and warm-invocation monotonicity)

## Constraints

- The route must be `Method: ANY` on `/uptime` in template.yaml. A `GET /uptime` route would make API Gateway return its own 404 for other methods, so the required 405 with Allow would never be produced, and QA tests of the template would fail.
- The 405 response must include the header `Allow: GET`. Only GET is permitted, and any other method, including HEAD and OPTIONS, returns 405.
- The start time must be captured once at module scope, never inside the handler. Uptime must grow across warm invocations of the same container and must not reset per request.
- `uptimeSeconds` must be a JSON number (not a string), non-negative, and derived from a monotonic clock or a start timestamp that cannot make the value negative.
- Every response, including 405 and 404, must set Content-Type application/json and `Cache-Control: no-store`, so clients and intermediaries cannot serve a stale uptime.
- The body must always be a JSON string, and error bodies must use { error: { code, message } } without leaking internals. Unexpected exceptions must return 500 with a generic message.
- The handler must read the HTTP API v2 payload fields (requestContext.http.method, rawPath), not the REST API v1 fields (httpMethod, path).
- No runtime dependencies, no hardcoded account ids, regions or secrets, and no IAM permissions beyond the basic execution role. There must be no UI and no other endpoints.
- Tests must run with the built-in node:test runner with no network or AWS access, and must not rely on real elapsed time (inject or fake the clock).
