# Architecture Design — Add a cancel booking endpoint that refunds payment

## Requirement

Add a cancel booking endpoint that refunds payment

## Decision

Implement a cancel booking endpoint in the payment module following hexagonal architecture. The endpoint will accept a booking ID and a cancel reason, validate that the booking exists and is in a cancellable state, then trigger a refund through the payment gateway adapter. The flow: REST controller (PaymentCancelController) -> application service (CancelBookingService) -> port interface (RefundPort) implemented by a gateway adapter (StripeRefundAdapter or similar). The service will first check booking status via an existing booking status port (BookingStatusPort), then call the refund port, and finally update the booking status to CANCELLED via a booking update port (BookingUpdatePort). The refund transaction ID and status will be persisted in a new 'refund' table managed by Liquibase. The OpenAPI spec will define the endpoint POST /bookings/{bookingId}/cancel with a request body containing reason, and a response indicating refund status. Integration tests will use a mock payment gateway, unit tests will cover service logic and state transitions.

## Constraints

- Endpoint must be idempotent: calling cancel twice with the same booking ID must return the same result and not issue a second refund.
- Refund must be processed only if the booking is in a state that allows cancellation (e.g., CONFIRMED, not already CANCELLED or COMPLETED); otherwise return a 409 Conflict.
- Refund amount must be derived from the original booking payment amount, not from client input.
- Payment gateway call must be wrapped in a try-catch; on gateway failure, the booking must not be marked CANCELLED and the endpoint returns a 502 Bad Gateway.
- The refund transaction ID from the gateway must be stored in the refund table; if the gateway returns no transaction ID, the operation must fail and roll back.
- All database changes must be applied via Liquibase changesets; no manual DDL or ORM auto-DDL is allowed.
- The OpenAPI spec must be the single source of truth for the endpoint contract; no separate manual API documentation is allowed.
- The service must not call the payment gateway directly; it must go through the RefundPort interface to keep the hexagonal boundary.
- Integration tests must use a mock payment gateway and an embedded database; no real payment or production credentials are allowed in tests.
- The response must include the refund status (e.g., PENDING, SUCCEEDED, FAILED) and a refund ID if available, matching the OpenAPI schema.
