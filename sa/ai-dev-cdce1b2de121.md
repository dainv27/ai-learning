# Architecture Design — Add a cancel booking endpoint that refunds payment

- Workflow: `ai-dev-cdce1b2de121`
- Repository (logical): `booking-service`
- Module: `payment`

## Requirement

Add a cancel booking endpoint that refunds payment

## Decision

Implement a synchronous cancel-booking-and-refund flow in the payment module. The REST adapter receives POST /bookings/{bookingId}/cancellation, delegates to CancelBookingRefundUseCase, which marks the booking cancelled via BookingCancellationPort, loads the booking payment, creates a Refund with status PENDING and an outbox message in the same transaction, calls PaymentGatewayRefundPort to execute the refund, updates the Refund to COMPLETED or FAILED, and publishes a RefundCompleted domain event. Idempotency is enforced by a unique constraint on (bookingId, idempotencyKey).

## Constraints

- The OpenAPI spec is the source of truth for the endpoint; the generated BookingCancellationApi interface must not be manually modified.
- A unique database constraint on (booking_id, idempotency_key) must enforce that retrying a request with the same bookingId and Idempotency-Key returns the existing refund result and never invokes PaymentGatewayRefundPort a second time.
- Refund record creation and outbox message insertion must occur in the same transaction before any call to PaymentGatewayRefundPort; if the transaction fails, no gateway call may be made.
- RefundStatus transitions are restricted to PENDING -> COMPLETED and PENDING -> FAILED; any attempt to set another transition must be rejected by the domain.
- The booking cancellation must be committed independently of the gateway refund result; a payment gateway failure must not roll back the cancelled booking and must leave the refund in a retryable FAILED/PENDING state.
- Refund amount must be validated against the original BookingPayment amount and currency; a refund larger than the original paid amount must fail with a domain validation error.
- All schema changes, including the refund table, idempotency unique constraint, and outbox table, must be added via Liquibase changesets; JPA auto-DDL must be disabled in all environments.
- PaymentGatewayRefundPort adapters must not contain business logic and must use only sandbox/WireMock endpoints in tests; no production payment gateway credentials may be stored in the repository.
- The application and domain layers must have no dependency on Spring annotations or servlet/HTTP classes; all inbound and outbound adapters must be in the adapter layers.
