# Test Design — Create a tiny AWS Lambda (Node.js 22, API Gateway HTTP API) with GET /uptime returning JSON {"uptimeSeconds": <number of seconds since the function container started>}. Any other method returns 405. No UI.

- Workflow: `ai-dev-8439078d4d3d`
- Repository (logical): `time-api`
- Module: `lambda`

## Requirement under test

Create a tiny AWS Lambda (Node.js 22, API Gateway HTTP API) with GET /uptime returning JSON {"uptimeSeconds": <number of seconds since the function container started>}. Any other method returns 405. No UI.

## Objective

Verify that GET /uptime returns JSON {"uptimeSeconds": <non-negative number>} measured from container start, that every other method returns 405 with Allow: GET, and that the architect constraints hold: v2 event fields, headers on every response, generic 500, a module-scope monotonic start, and a SAM route declared as ANY.

## Approach

Black-box tests of the exported handler and createHandler with realistic HTTP API v2 events and an injected fake clock, so no real time passes. Unit tests cover computeUptimeSeconds and the module-scope start. Static checks read template.yaml and package.json for Method ANY, runtime, timeout, memory, outputs, no extra IAM policies and no runtime dependencies. All assertions come from the requirement and constraints, not from the implementation internals. Header names are compared case-insensitively because HTTP headers are case-insensitive.

### TC-001 — GET /uptime returns 200 with numeric uptimeSeconds

1. Create a handler with a fake clock 12.5s after start
2. Invoke with a v2 GET /uptime event
3. Parse the body

**Expected:** Status 200, body is a JSON string whose only key is uptimeSeconds, a number of about 12 seconds (>=12 and <13).

### TC-002 — Every response carries JSON content type and Cache-Control no-store

1. Invoke GET /uptime, POST /uptime and GET /other
2. Inspect the headers and the body type

**Expected:** Each response has content-type application/json (charset utf-8), cache-control no-store and a string body.

### TC-003 — POST, PUT, DELETE and PATCH return 405 with Allow: GET

1. Invoke /uptime with each method

**Expected:** Status 405 and an Allow header equal to GET.

### TC-004 — HEAD and OPTIONS also return 405

1. Invoke /uptime with HEAD and OPTIONS

**Expected:** Status 405 with Allow: GET.

### TC-005 — 405 body uses the error shape

1. Invoke POST /uptime
2. Parse the body

**Expected:** The body has error.code as a non-empty string and error.message as a non-empty string, and no uptimeSeconds.

### TC-006 — Unknown path returns 404 with the error shape

1. Invoke GET /nope and GET /

**Expected:** Status 404 with error.code and error.message.

### TC-007 — Warm invocations are non-decreasing and do not reset

1. Create one handler with a fake clock
2. Invoke it three times, advancing the clock between calls

**Expected:** The values are 0, 3 and 10 (about), never decreasing. The default handler called twice also returns non-decreasing values.

### TC-008 — Unexpected exception returns generic 500

1. Create a handler whose clock throws an Error with a secret message
2. Invoke GET /uptime

**Expected:** Status 500, standard headers, error body with a code, and the body does not contain the secret text or a stack trace.

### TC-009 — Handler reads v2 fields, not v1

1. Send a v1-shaped event with only httpMethod and path
2. Send an empty event

**Expected:** The v1 event is not served as 200. Neither call throws or returns 500, and both return a JSON error body.

### TC-010 — GET with a query string still succeeds

1. Invoke GET /uptime with rawQueryString set

**Expected:** Status 200 with a numeric uptimeSeconds.

### TC-011 — computeUptimeSeconds is pure, whole-second and never negative

1. Call computeUptimeSeconds with equal times, 5000ms, 5999ms, a reversed pair and non-finite input

**Expected:** Results 0, 5, about 5 (>=5 and <6), 0 for the reversed pair, and a number >=0 for non-finite input.

### TC-012 — Container start captured once at module scope

1. Read containerStartMs
2. Invoke the default handler several times
3. Re-read containerStartMs and compare the handler's uptime with the elapsed time since the start

**Expected:** containerStartMs is a finite number that is unchanged after invocations. The default handler's uptime is within 1s of the time elapsed since containerStartMs.
